## 2. למה מחוץ לקובץ ה־HTML

הקובץ `OtzariaLinker.html` אינו פונה לרשת ([`AGENTS.md`](../AGENTS.md) §2.1). זה נאכף בשלוש שכבות: הסריקה ב־
`scripts/package-release.mjs` נכשלת על `fetch(` חשוף, `XMLHttpRequest` ודומיהם; ה־CSP מתיר `connect-src` רק ל־`blob:`
ו־`data:`; ובדיקות ה־E2E רצות במצב לא מקוון. מודל שפה מאחורי API לא נגיש משם, ואסור לפרוץ את זה.

לכן:
- `src/ai/` היא שכבה **טהורה** (`ai` בטבלה של [`ARCHITECTURE.md`](ARCHITECTURE.md)): מייבאת רק `core` ו־`linking`,
  בלי Preact, בלי DOM, בלי מודול של Node ובלי קריאת רשת. מי שמממש ספק אמיתי הוא **המארח** (CLI, מארח תוסף), מחוץ ל־`src/`.
- אף שכבה של האפליקציה אינה רשאית לייבא את `ai`, ובדיקת הארכיטקטורה עוקבת אחרי כל הייבואים מ־`src/app/main.tsx` (כולל
  ה־Worker המוטמע) ומוודאת שאינם מגיעים אליה. לכן הגודל של ה־HTML לא השתנה בגלל השכבה הזו.
- בדיקה נוספת סורקת את `src/ai` ונכשלת על `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`,
  `importScripts`, כתובת `http(s)://` או ייבוא `node:`.

## 3. העיקרון: המודל אינו יוצר קישור

- המודל רואה רק את **המועמדים של המנועים**: לכל הצעה, מזהה, שורת המקור, ורשימה ממוספרת של מקומות (אפשרות 0 היא הבחירה
  של המנוע, ואחריה החלופות שלו).
- הוא יכול לענות רק: `accept` עם מספר אפשרות, `reject` או `unsure`, עם ביטחון 0–1 ונימוק קצר.
- הבודק ממפה את מספר האפשרות **למקום שהמנוע עצמו יצר** (אותו אובייקט `LinkSide`). שם ספר, מזהה ספר, שורה או הפניה
  שהמודל כותב בעצמו לא נקראים אף פעם; החלטה שמוסיפה שדה כזה נדחית כולה.
- ההחלטות הן **המלצה לבודק האנושי**. הן לא מאשרות הצעה, לא יוצרות קישור, ולא משנות את דרגת הביטחון של המנוע. כל קישור
  עדיין נוצר רק דרך `history.commit` ([`AGENTS.md`](../AGENTS.md) §2.5), באישור של המשתמש. גם "ודאית" נשארת כפי שהמנוע קבע.
- הנימוק של המודל הוא טקסט לא מהימן: מציגים אותו כטקסט רגיל בלבד (לא HTML), וקוצצים אותו ל־300 תווים.

## 4. הממשק המוצע

```ts
// src/ai/types.ts
interface AiProvider {
  readonly id: string;                 // ההסכמה ניתנת לפי מזהה ספק
  readonly remote: boolean;            // האם התוכן יוצא מהמחשב (מוצג כשמבקשים הסכמה)
  readonly models: readonly string[];  // מודל שאינו ברשימה נדחה לפני כל בקשה
  complete(request: AiRequest, signal: AbortSignal): Promise<AiResponse>;
}
interface AiRequest { model; system; user /* JSON של המועמדים */; responseSchema /* AI_ANSWER_SCHEMA */; maxOutputTokens }
interface AiResponse { text /* JSON, נבדק תמיד */; usage?: { inputTokens; outputTokens } }
class AiProviderError { kind: "auth" | "rate-limit" | "network" | "server" | "bad-request" | "timeout"; retryAfterMs? }

interface AiConfig {
  enabled: boolean;                    // ברירת מחדל false
  providerId: string; model: string;   // בחירת מודל
  scope: "refs" | "refs+text";         // מה מותר לשלוח
  skills: AiSkill[];                   // כללים מוגדרים, לפי מנוע
  limits: AiLimits;                    // בקשות, מועמדים לבקשה, תווים לבקשה, תקציב טוקנים, פלט, זמן קצוב, ניסיונות חוזרים
}
interface AiConsent { providerId: string; scope: "refs" | "refs+text"; grantedAt: string }

runAiReview({ config, provider, consent, suggestions, text?, isValidTarget?, signal?, secrets?, sleep?, progress? })
  → Promise<AiRunReport>   // status, decisions, rejections, notReviewed, usage, messages (בעברית)
```

סכמת התשובה (`AI_ANSWER_SCHEMA` ב־`src/ai/request.ts`): אובייקט סגור `{"decisions": [...]}`, וכל החלטה אובייקט סגור עם
`id`, `verdict` (`accept`/`reject`/`unsure`), `option` (מספר שלם, או `null` כשאין קבלה), `confidence` (0–1) ו־`reason`.
ספק שתומך בפלט מובנה מעביר אותה כסכמה; ספק שאינו תומך מקבל אותה גם בהוראות. בכל מקרה התשובה עוברת את הבודק.

### 4.1 סדר השערים (`runAiReview`)

1. `enabled` חייב להיות `true` (אחרת `disabled`, בלי שום בקשה).
2. הספק הוא הספק שהוגדר, והמודל ברשימה שלו (אחרת `config-invalid`).
3. **הסכמה**: בלי `AiConsent` שמכסה את הספק ואת ההיקף, לא נשלח דבר (`consent-required`). הסכמה ל־`refs+text` מכסה
   גם `refs`; הסכמה לספק אחד אינה מכסה ספק אחר.
4. לפני **כל** בקשה (גם ניסיון חוזר): ביטול, מגבלת מספר הבקשות, והתקציב — הטוקנים שכבר נוצלו, ועוד ההערכה של הבקשה
   **ועוד כל מכסת הפלט** שלה. בקשה שעלולה לעבור את התקציב לא נשלחת (`budget-exhausted`).
5. הבקשה רצה תחת זמן קצוב ותחת האות של המשתמש, **במרוץ**: גם ספק שמתעלם מהאות לא יכול לעכב את ההרצה.
6. שגיאה שאפשר לנסות שוב (קצב, רשת, שרת, זמן) נוסה שוב עד `maxRetries`, עם המתנה לפי `Retry-After` או 1, 2, 4… שניות
   (עד 30). שגיאת הרשאה או בקשה שגויה עוצרת מיד (`error`).
7. כל תשובה עוברת את הבודק (§5). עצירה שומרת את מה שכבר נבדק, ומחזירה את השאר ב־`notReviewed`.

### 4.2 מה נשלח

- `refs` (ברירת המחדל): שמות הספרים, מספרי שורות (1-based), ה־heRef, הציון וסוג הקשר, ו**הקוד** של כל נימוק של המנוע
  (`dh/exact`). לא נשלח טקסט של ספר — גם לא המשפט של הנימוק, כי הוא עשוי לצטט את השורה ("ההפניה בטקסט: …").
- `refs+text`: בנוסף, קטע קצר מכל שורה (בלי תגים, עד `maxSnippetChars`, ברירת מחדל 300) ומשפטי הנימוק. רק בהסכמה
  להיקף הזה; בלעדיה הטקסט לא נשלח גם אם המארח מסר פונקציה שקוראת אותו.
- הבקשה דטרמיניסטית: אותן הצעות ואותן הגדרות נותנות אותו טקסט. אפשר לשמור אותה, להשוות ולבדוק מה בדיוק יצא.

### 4.3 הגנת המפתח

- אין שדה מפתח ב־`AiConfig`, בבקשה, בדוח או בקובץ פרויקט. המפתח שייך לספק, והמארח קורא אותו ממשתנה סביבה או ממאגר
  מפתחות של מערכת ההפעלה.
- `checkAiConfig` דוחה קובץ הגדרות שיש בו שדה שנראה כמפתח (`apiKey`, `api_key`, `x-api-key`, `accessToken`, `password`,
  `secret` ודומיהם, בכל עומק), כדי שמפתח לא יישמר בטעות בקובץ שמשתפים.
- כל הודעה בדוח עוברת `redactSecrets`: הערכים שהמארח מסר ב־`secrets`, וגם צורות נפוצות של מפתח (`sk-…`, `AIza…`,
  `?key=…`, `Bearer …`). יש בדיקה שבה שגיאת הספק מצטטת את המפתח, והוא לא מופיע בדוח.

## 5. הבודק הדטרמיניסטי (`validateAiAnswer`)

רץ אחרי **כל** תשובה, בלי רשת ובלי מודל. נשארת רק החלטה ש:
- התשובה כולה היא JSON (או JSON בתוך גדר אחת של ` ```json `); לא מחפשים JSON בתוך טקסט חופשי (`ai/invalid-json`);
- המבנה הוא בדיוק `{"decisions": [...]}` (`ai/invalid-shape`);
- המזהה הוא של הצעה **שנשלחה בבקשה הזו**. מזהה שהמודל המציא נדחה, ולא מוחזר בדוח (`ai/unknown-candidate`);
- אין בה שדה מעבר לחמשת השדות (`ai/unexpected-field`) — כך מודל לא יכול "להציע" ספר או שורה משלו;
- ההכרעה, הביטחון והנימוק תקינים (`ai/invalid-verdict`, `ai/invalid-confidence`, `ai/invalid-reason`);
- ב־`accept`, מספר האפשרות קיים (`ai/invalid-option`), והמקום של המנוע עדיין תקין: שורה שלמה לא שלילית, סוף שאינו לפני
  ההתחלה, ו־`isValidTarget` של המארח, אם נמסר (שורה שקיימת, שאינה כותרת וכו') (`ai/invalid-target`);
- זו ההחלטה הראשונה על אותה הצעה (`ai/duplicate-decision`).

הצעה גדולה מבקשה שלמה לא נשלחת (`ai/candidate-too-large`).

## 6. רעיונות מ־YairDaniel11/Otzariya_Link_Maker (רעיונות בלבד)

המאגר מחוץ לארגון Otzaria, ולכן **רעיונות בלבד, בלי קוד** ([`AGENTS.md`](../AGENTS.md) §2.7;
[`REUSE_MATRIX.md`](research/REUSE_MATRIX.md) §2.7, commit `4f8baa08958add24e782109de02b80fb091540b9`, נבדק דרך ה־API
הציבורי של GitHub ב־26.11.2026). שם ה־AI מציע **כללי מבנה** לספר (פרופיל כותרות), ולא קישורים. הרעיונות שאומצו כאן:

- ה־AI אופציונלי לגמרי; בלעדיו הכלי עובד, ובלעדיו לא נשלח דבר.
- ברירת המחדל שולחת תקציר בלבד, ושורות דוגמה רק בבחירה מפורשת — כאן: `refs` מול `refs+text`, עם הסכמה לכל היקף.
- כל הצעה של המודל עוברת בדיקה דטרמיניסטית לפני שימוש (שם: אימות הפרופיל והרצה יבשה עם אחוז כיסוי).
- שכבת התקשורת מוזרקת (שם: פונקציות HTTP), כך שבודקים בלי רשת — כאן: `AiProvider` ו־`MockAiProvider`.
- ניסיונות חוזרים לפי `Retry-After`, והבחנה בין חריגת מכסה אמיתית להגבלת קצב.
- הסבר בעברית לכל שגיאת ספק, עם מה לעשות.

מה **לא** אומץ: שמירת המפתח בקובץ מקומי בלי הצפנה (כאן המפתח אינו בקובץ הגדרות בכלל), וקריאה לרשת מתוך הכלי עצמו.

## 7. DEFERRED ותוכנית המשך מדויקת

אלה לא בוצעו בכוונה. כל אחד מהם הוא שלב נפרד, עם תנאי קבלה.

1. **ספק אמיתי** — DEFERRED. לא הוספנו כי אסור להשתמש בשירות בתשלום או במפתח בעבודה הזו, ובלי מפתח אי אפשר לבדוק אותו
   באמת. התוכנית: קובץ אחד לכל ספק **מחוץ ל־`src/`** (למשל `tools/ai-providers/<id>.ts`, בשכבת ה־CLI), שמממש
   `AiProvider` עם `fetch` של Node, ממפה סטטוס HTTP ל־`AiProviderError` (401/403 → `auth`, 429 → `rate-limit` עם
   `Retry-After`, 5xx → `server`, 400 → `bad-request`), ומעביר את `responseSchema` כפלט מובנה של הספק. המפתח ממשתנה
   סביבה (`OTZARIA_LINKER_AI_KEY` או משתנה לפי ספק), ונמסר ל־`runAiReview` ב־`secrets`. תנאי קבלה: בדיקות של הספק עם
   `fetch` מוזרק (בלי רשת) לכל מיפוי סטטוס; הרצה ידנית אחת מתועדת, באישור הבעלים ובמפתח שלהם.
2. **חיבור ל־CLI / לליבה הלא־גרפית** — DEFERRED. ה־CLI נבנה במקביל בענף אחר. התוכנית: פקודה כמו
   `ai-review --suggestions <file.json> --config <ai.json> --consent <provider>:<scope>` שקוראת הצעות שהמנוע הפיק (או
   מריצה אותו דרך `runPair` ב־`linking/adapters.ts`), מריצה `runAiReview`, וכותבת דוח JSON: ההחלטות, הדחיות, `notReviewed`,
   השימוש בטוקנים והבקשות עצמן (בלי מפתח). ההסכמה ניתנת בדגל מפורש בכל הרצה, ולא נשמרת כברירת מחדל. תנאי קבלה: הרצה עם
   `--provider mock` ב־CI; בלי דגל ההסכמה — שום בקשה; קוד יציאה שונה מאפס כשהסטטוס אינו `done`.
3. **הצגה בכלי** — DEFERRED. ה־HTML לא פונה לרשת, ולכן הדרך היחידה היא **ייבוא** של דוח ה־CLI כקובץ: הצגת ההמלצה ליד
   כל הצעה (כטקסט בלבד), סינון "המודל לא הסכים", בלי אישור אוטומטי. זה משנה את `state` ואת `ui`, ודורש החלטה (ADR) לפני.
4. **מדידה לפני שימוש** — DEFERRED. לפני שממליצים על ההמלצות, למדוד על הצעות שיש להן תשובה ידועה (הקישורים במסד,
   כמו ב־[`LIBRARY_BENCHMARK.md`](validation/LIBRARY_BENCHMARK.md)) כמה פעמים המודל צדק, טעה, או "לא בטוח", לפי מנוע ולפי דרגת ביטחון. בלי מדידה כזו
   ההחלטות הן רעש, ולא מציגים אותן.
5. **תקציב במטבע** — DEFERRED. התקציב היום בטוקנים. מחיר לטוקן תלוי במודל ומשתנה; כשיהיה ספק אמיתי, ההמרה תהיה בספק
   (מחיר לכל מודל בקובץ ההגדרות של המארח), והמגבלה תישאר `maxTotalTokens`.
6. **מטמון ותיעוד בקשות** — DEFERRED. כיוון שהבקשה דטרמיניסטית, אפשר לשמור תשובות לפי גיבוב של הבקשה ולא לשלם פעמיים.
